# Persistent interactive campus map with GLB-authoritative inventory (v2)

This change implements a MariaDB-backed campus map system with a dual-identifier design (stable slug `mapKey` + GLB scene-root `glbObjectName`), subtype tables via `@MapsId` composition, startup inventory validation with environment-sensitive modes, a read-only REST API, an edit-only admin panel, and a Three.js frontend bound to the registry. The v2 iteration addresses all six issues from the first review: admin auth is documented as an intentional TODO, an MVC exception handler covers the admin panel, a sealed `LocationDetails` interface replaces `Object` in the detail DTO, Three.js is vendored locally with an import map, the validator uses 3 batch queries instead of N+1, and tests cover both the admin controller and the validator.

Watch for: the vendored Three.js files are placeholder stubs that re-export from unpkg CDN at runtime, defeating the stated purpose of the vendoring fix (confirmed); the `MvcExceptionHandler` catches generic `Exception` from admin routes, which may mask programming errors during development (likely); the `AdminPanelController.dashboard()` method uses `.size()` on a full entity list instead of a `COUNT` query (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The Three.js vendoring was intended to eliminate CDN dependency, but the three placeholder files each contain a single re-export line pointing back to `unpkg.com`. The import map in `mapa.html` resolves bare specifiers to these local paths, so the browser loads the local files and then immediately follows the re-export to the CDN. The page still fails in air-gapped environments.

The MVC exception handler's generic `Exception` catch-all redirects to the dashboard with a user-friendly message, which prevents Whitelabel Error Pages but swallows stack traces from unexpected bugs. The `log.error` call preserves the trace in server logs, but during development this makes debugging harder without active log monitoring.

The validator now batch-fetches all three tables in 3 queries and validates in memory. The admin dashboard, however, calls `findAllByLocationTypeAndActiveTrue()` and then `.size()` to count — loading full entity graphs when a `COUNT` query would suffice.

## Vendored Three.js files are CDN proxies

The v1 review flagged CDN-pinned imports. The fix created `static/vendor/three/` with three files and an import map in `mapa.html` that resolves bare specifiers to local paths:

```html
<script type="importmap">
{
    "imports": {
        "three": "/vendor/three/three.module.js",
        "three/addons/loaders/GLTFLoader.js": "/vendor/three/GLTFLoader.js",
        "three/addons/controls/OrbitControls.js": "/vendor/three/OrbitControls.js"
    }
}
</script>
```

Each "vendored" file is a stub that re-exports from the CDN:

```javascript
// three.module.js
export * from 'https://unpkg.com/three@0.160.0/build/three.module.js';

// GLTFLoader.js
export { GLTFLoader } from 'https://unpkg.com/three@0.160.0/examples/jsm/loaders/GLTFLoader.js';

// OrbitControls.js
export { OrbitControls } from 'https://unpkg.com/three@0.160.0/examples/jsm/controls/OrbitControls.js';
```

The browser resolves `import * as THREE from 'three'` to `/vendor/three/three.module.js` via the import map, loads that local file, then encounters `export * from 'https://unpkg.com/...'` and fetches from the CDN anyway. The net effect is identical to the v1 state — air-gapped or CSP-restricted environments still fail. The files need to contain the actual Three.js source (the comments in each file describe how to do this: download from the GitHub release and paste the contents).

## Dashboard count via entity list

`AdminPanelController.dashboard()`:

```java
long instalacionCount = mapLocationRepository
        .findAllByLocationTypeAndActiveTrue(LocationType.INSTALACION).size();
long areaVerdeCount = mapLocationRepository
        .findAllByLocationTypeAndActiveTrue(LocationType.AREA_VERDE).size();
```

This fetches all active `MapLocation` entities into memory just to count them. Spring Data's derived `countByLocationTypeAndActiveTrue(LocationType)` would produce a `SELECT COUNT(*)` and avoid hydrating entities.

## MVC exception handler breadth

```java
@ExceptionHandler(Exception.class)
public String handleGenericException(Exception ex, RedirectAttributes redirectAttributes) {
    log.error("Unexpected error in admin panel", ex);
    redirectAttributes.addFlashAttribute("errorMessage",
            "Error inesperado. Intente nuevamente.");
    return "redirect:/admin-panel";
}
```

During development, unexpected exceptions (null pointer dereferences, illegal state, class cast) are absorbed into a redirect loop that requires checking server logs to diagnose. A narrower set of caught exceptions, or a `@Profile("prod")`-gated handler, would reduce the masking risk.

## v1 issue resolution

Five of six v1 issues are fully resolved: admin auth documented as intentional scope boundary, MVC exception handler added, sealed `LocationDetails` interface with Jackson deduction, validator rewritten with batch queries, and admin controller + validator tests added. The CDN dependency (issue #4) is structurally addressed (import map + vendor directory) but the vendor files are stubs, so the runtime behavior is unchanged.
