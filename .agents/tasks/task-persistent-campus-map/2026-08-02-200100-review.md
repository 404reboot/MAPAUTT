# Persistent interactive campus map with dual-identifier Instalacion model (v3)

This change introduces a MariaDB-backed campus map system for the UTTECAM campus. The domain model generalizes the earlier "Edificio" concept into an `Instalacion` supertype covering buildings, sports facilities, parking, services, and paths, alongside an `AreaVerde` subtype for green areas. A dual-identifier design gives each location both a stable application slug (`mapKey`) and a GLB scene-root name (`glbObjectName`), decoupling database identity from 3D model evolution. The inventory validator enforces `fail` mode in production and `warn` in development, per the requirement of strict validation with a usable dev fallback. The Three.js frontend stubs are explicitly marked as placeholders that throw on import, with graceful degradation in the viewer.

Watch for: the admin panel has no authentication — all `/admin-panel/**` routes are network-accessible to any client that can reach the server (confirmed, documented as intentional scope boundary).

**Verdict**: APPROVED

## High-level view

The domain model uses `MapLocation` as a shared identity table with `Instalacion` and `AreaVerde` detail tables joined via `@MapsId`. The `FacilityType` enum sub-classifies installations (BUILDING, SPORTS, PARKING, SERVICE, PATH, WATER_LAND, OTHER), satisfying the requirement to broaden beyond the original "Edificio" concept. Both identifier columns carry unique constraints enforced at the DDL level.

The inventory validation subsystem loads `map-locations.json` into an in-memory registry at construction time, then cross-references it against the database in a 3-query batch on `ApplicationReadyEvent`. Production fails fast on any mismatch; development logs warnings and continues. This directly implements the "strict in prod, usable fallback in dev" requirement without needing profile-conditional beans.

The Three.js vendor stubs now throw immediately on import, and `mapa.js` wraps the import in a try/catch that displays a user-facing notice when the library is unavailable. No network request leaves the browser — the v2 CDN leak is fully resolved.

All three v2 issues (CDN re-export stubs, dashboard entity-list count, generic exception catch-all) are resolved. The vendor files throw instead of fetching; the dashboard uses `countByLocationTypeAndActiveTrue()`; the MVC exception handler is narrowed to `LocationNotFoundException` and `LocationTypeMismatchException` only.

## Unauthenticated admin surface

The `AdminPanelController` class-level Javadoc explicitly flags this as a known gap:

```java
/**
 * TODO: This controller has no authentication or authorization.
 * All routes under /admin-panel are accessible to any network client.
 * ...restrict network access to this path at the infrastructure level
 */
```

The edit endpoints accept `@Valid` command objects and write directly to the database. Without auth, any client that can reach the server can modify display names, descriptions, operational statuses, and surface areas for all 54 locations. The Javadoc's mitigation (firewall/ingress rules) is valid but requires external coordination before production exposure.
